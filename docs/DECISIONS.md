## 2026-11-04 — architecture decisions (approved by the client)

- ERPNext v16 is the core ERP on Frappe v16 and MariaDB 11.8; pinned tags, never `develop`.
- All factory-specific work lives in the custom Frappe app `factory_ops`; no ERPNext core changes.
- UI: ERPNext Desk for Phase 1; Frappe UI (Vue 3) evaluated for shop-floor pages; `apps/web` (React)
  frozen as design reference — the React/TanStack/Lingui libraries above are no longer part of the build.
- Hosting: self-hosted VPS in Mumbai, client-owned account, FlowHQ admin access; dev/staging/prod.
- Licensing: GPL-3.0 accepted; `factory_ops` released under GPL-3.0 (lawyer to confirm).
- QC hold is modelled as quarantine warehouses + a QI-gated QC Release (DATABASE_AND_WORKFLOW_DESIGN.md §3).

## 2026-11-04 — Phase 1 build decisions (Milestones 1–2)

**D-001 Pins verified.** Frappe `v16.55.2` (3d1284c) and ERPNext `v16.53.0` (9cd11b1) are installed
from their tags. Frappe v16 requires Python `>=3.14,<3.15` and Node `>=24`; we use CPython 3.14.6 and
Node 24.22.2. MariaDB 11.8.9 (Docker `mariadb:11.8`, the frappe_docker image). India Compliance and
ecommerce_integrations are **not installed yet**: India Compliance waits for a real GSTIN; the
marketplace app is Phase 7.

**D-002 Development topology.** MariaDB and the cache/queue run in Docker with the same server flags
as frappe_docker's devcontainer (`deploy/dev/compose.yaml`). bench runs on the host as a non-root
`frappe` user instead of inside the `frappe/bench` container, because this environment's outbound
proxy is reachable only from the host. Production still uses frappe_docker images (deployment runbook).

**D-003 Test site.** Automated tests run on a separate `test.localhost` site with ERPNext's own test
bootstrap (`_Test Company`); the development site `factory.localhost` never receives test data.

**D-004 Valkey instead of Redis.** Valkey 8.1 (BSD-3-Clause), a Redis-protocol-compatible fork, is
used for cache and queue in development and will be in production. This removes the Redis 8
licence question (RSALv2/SSPLv1/AGPLv3 choice) entirely. Verified: Frappe v16 site, login, Desk and
the full factory_ops test suite run on Valkey 8.1. Fallback if a problem appears: `redis:7.2`
(last BSD release) — record it here if used.

**D-005 Setup in code, re-applied on migrate.** Custom fields, roles, warehouse types and custom
permissions are declared in Python (`factory_ops/setup/`) and applied by `after_install` and
`after_migrate`, rather than exported fixture JSON. Reason: they are reviewable diffs, idempotent,
and a fresh site and an upgraded site converge to the same state. Fixtures remain for things edited
in Desk (workspaces, later workflows).

**D-006 QC lifecycle confirmed by spike; one QI per QC Release.** The spike
(`tests/test_spike_qi_lifecycle.py`, 8 tests, all pass on v16.53.0) showed a Quality Inspection can
reference a draft Material Transfer and ERPNext then gates its submission. A QI is bound to exactly
one Stock Entry, so a partial release and the later rejection of the remainder each need their own
QI. ERPNext ignores the QI when `inspection_required = 0`, so the reject and conditional paths are
checked by `factory_ops` itself.

**D-007 Permissions ERPNext v16 does not give by default.**
- `Batch`: create + read for Stock User and Manufacturing User. Only Item Manager can create a Batch
  in v16, yet a batch is auto-created on every receipt or production output, so receiving failed
  without it. No write is granted, so expiry dates stay editable by Item Manager only.
- `Serial and Batch Bundle`: the same rights Stock User has, for QC Officer and QA Manager. Submitting
  a QC Release's transfer creates bundles as the session user. A bundle on its own moves no stock.
- `Batch.fo_qc_status` is at permlevel 1 with read-only access for operational roles, so no user can
  write the derived status through the API.

**D-008 Segregation scope.** Whoever made the first inward movement of a batch (and, for production,
the Work Order owner) cannot Release, Partially Release or Conditionally Release it. They *may*
reject it: rejecting your own receipt reduces risk, it does not create it.

**D-009 A guard flag, not a field, unlocks the release transfer.** The QC Release sets a process-local
`frappe.flags` value while submitting its own Stock Entry. A client cannot set that through the API;
setting `fo_qc_release` on a Stock Entry does not unlock anything (test 14).

## 2026-11-05 — validation round and Milestone 3 (purchase and inventory)

**D-010 Send for Re-test is its own document (QC Retest).** QA Manager only; the only route from a
Rejected warehouse back to QC Hold (the earlier generic "QA Manager may transfer" path in the guard
was removed). The re-tested material is held stock again: it needs a new QC Release with a new,
accepted QI. ERPNext itself refuses reuse of the old QI (it is bound to the old transfer).

**D-011 Pick List.** ERPNext computes suggested locations in `before_save`, after `validate`, and
without a parent warehouse it suggests QC Hold stock. factory_ops defaults the parent warehouse to the
company's USABLE group and checks locations again in `before_save` and `before_submit`.

**D-012 QC items are received only by Purchase Receipt.** A stock-updating Purchase Invoice would
bypass supplier batch, dates and COA capture, so it is refused for QC items (non-QC items unaffected).

**D-013 Supplier batches.** On GRN submit factory_ops creates the Batch from the receipt row
(supplier batch no, manufacturing and expiry dates, COA, supplier) before ERPNext builds the batch
bundle, so the batch carries the supplier's dates from the start; ERPNext's shelf-life-based expiry
is not used for bought material. Supplier batch no and mfg date are mandatory for QC items with batch
tracking; expiry for items with expiry tracking; COA for item groups flagged "COA required" (RM).

**D-014 Purchase approval = submitting the PO.** Enforced in `before_submit`: the submitter must not be
the creator and must have a Purchase Approval Limit ≥ the PO's base grand total. No Frappe Workflow is
needed for this rule. A Factory Ops Settings switch can turn enforcement off (audited); it is used only
by one ERPNext test helper that submits its own PO.

**D-015 Defaults of new fields on existing Singles are back-filled on migrate.** A field added to a
Single DocType never gets its JSON default on an existing site (it reads as 0). This silently turned
approval enforcement off on the upgraded test site; `apply_setup` now writes defaults for unset fields.

**D-016 Stock Settings are set by factory_ops** (`configure_stock_settings`): batch tracking on (a fresh
v16 site has it off and cannot receive batch items), no negative stock, FEFO (Expiry), moving average,
stock reservation on, QI Stop actions. Tests use the same function.

**D-017 Extra read rights for QC roles:** Company (report filters resolve it) and Stock Ledger Entry
(read/report, for the Stock by QC Status and Stock Ledger reports). Both gaps were found in the
browser and HTTP checks, not by unit tests.

**D-018 GL reconciliation is tested on a perpetual-inventory company.** ERPNext's `_Test Company` has
perpetual inventory off (receipts post no GL). The acceptance test uses its own company created the
normal ERPNext way with perpetual inventory on, like the SAMPLE company.

**D-019 Development data and users.** `setup_dev_site` runs ERPNext's own setup wizard (SAMPLE company,
April–March FY) then the same master-data code the tests use. Sample users get random passwords
written to `sites/<site>/private/sample_users.json` (mode 600, outside the repository); creating them
refuses to run unless developer mode is on.

## Milestone 4: production (2026-11-05)

**D-020 Production is standard ERPNext.** Two BOMs per product (BULK from RM in kg; FG from BULK + PM in
units), two Work Orders, Material Transfer for Manufacture and Manufacture entries, ERPNext's own
process loss, batch creation and expiry from shelf life. Backflush is "Material Transferred for
Manufacture", so consumption follows what reached WIP (less returns), not the BOM figure. factory_ops
only adds the controls in `production/controls.py` and the batch label. Workflow:
`PRODUCTION_WORKFLOW.md`.

**D-021 Production warehouses are configuration.** ERPNext fills a Work Order component's source from the
item-group default warehouse. For QC groups that is the QC Hold warehouse (it is where purchases are
received), so every new Work Order was refused by the QC guard. Hard-coding "RM-STORES" in code was
rejected. Instead:
- a *Production Source Warehouse* field sits on Item Defaults (item beats group); without it, the
  QC release destination of the default warehouse is used;
- the WIP warehouse is a Company field;
- only rows ERPNext filled during this save are redirected. Rows typed by a user or set on the BOM are
  kept as entered and then checked by the guards, so a manual QC Hold or Rejected source is refused,
  never silently changed.
- Addendum (CI run 7): ERPNext can also fill a component from the *item's own* default warehouse,
  which may be a plain usable store. A configured production source wins over any value ERPNext
  filled, restricted or not. ERPNext's value is kept only when nothing is configured or derivable.

**D-022 Two-stage rule.** ERPNext's *Use Multi-Level BOM* defaults to on and would explode the bulk into
its raw materials, skipping bulk QC entirely (found by the first FG test run). New Work Orders whose BOM
holds a QC-controlled made component get it off; turning it on is refused on save and submit.

**D-023 Wastage is a Stock Entry Type, not every Material Issue.** The first draft required a reason on
every Material Issue, which would have mislabelled ordinary issues (to R&D, samples) as wastage. Now a
Stock Entry Type flagged *Wastage write-off* (seeded: "Wastage", purpose Material Issue) requires an
enabled Wastage Reason on every row and posts to the Company's *Wastage Expense Account*. A reason on any
other entry is refused, so wastage cannot be filed as an ordinary issue. Manufacture consumption and
process loss need no reason. Scrap from REJECTED keeps its disposal reason (G2).

**D-024 Test valuation method.** ERPNext's test bootstrap saves Stock Settings with FIFO on every test
run and refuses to change the valuation method once transactions exist. Our test setup used to set
Moving Average, so every *second* run on the same test site failed during test discovery. CI always
starts from a fresh site, so it never showed this. Tests now leave the valuation method to ERPNext's
bootstrap; real sites still get Moving Average from `setup_dev_site`.

**D-025 Batch label.** A standard Jinja Print Format on Batch, rendered by Frappe's Chrome PDF generator
on a 100 × 60 mm page. The page size and margins must be in the Print Format's `css` field (`@page`):
Frappe's Chrome generator reads them from there and otherwise applies 15 mm margins. A standard Print
Format is reloaded on migrate only when its `modified` timestamp changes. The QC status is printed as
a band, white on black for HOLD and REJECTED. Barcode/QR and ZPL are Phase 4.
